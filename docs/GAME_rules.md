# Party Games — Current Game Rules & Architecture

> Reference document for the "Party Games" real-time multiplayer engine in this repository.
> This file records the game currently implemented in the system and the architecture that should
> be kept improving it.

---

## 1. What "Party Games" currently is

**Party Games** is a mobile-first, real-time multiplayer **party / social-deduction game engine**
built with React 19, TypeScript, Tailwind CSS v4, Express, and Socket.IO.

- All players join from their own phones; there is no shared monitor or TV.
- The server is **authoritative**: it owns the full room state, secret roles, hidden words,
  submitted answers, and the phase state machine.
- Players receive a **masked public** state for the room and a **targeted private** state for
  themselves, so secret roles and hidden words cannot be snooped through dev tools or the network
  inspector.
- A 4-character room code + QR code are used for joining.
- A "next-round" loop lets a host replay a new round with a fresh role assignment.

## 2. Accepted rules for the system

These are the ground rules the engine currently implements and should continue to honor.

### 2.1 Player and room rules

- A room requires **3–12 players** for the Impostor game.
- The host creates the room; other players join by a **4-character room code**.
- Each player is assigned a **color index (0–5)** that loops by join order.
- Session tokens are generated by the server and used to keep a player's identity stable
  across reconnection.
- A player who disconnects can reconnect by a previous name or session token.
- If the host disconnects, a new active non-bot player is promoted to host.

### 2.2 Phase rules

The implemented round phases, in order, are:

1. `lobby` — players join; the host configures bots and launches.
2. `game-select` — the host selects a game (default: Impostor).
3. `reveal` — private role assignment.
4. `input` — players submit one-word clues.
5. `reveal-answers` — clues are revealed simultaneously.
6. `discussion` — timed group discussion.
7. `vote` — secret ballot.
8. `results` — tally reveal, role exposure, and standings.
9. `next-round` — new round (new word and new random impostor).

### 2.3 Impostor game rules

- **Role assignment:** one player is randomly selected as **The Impostor**; the other players are
  **Crew Members**.
- **Secrets:**
  - Crew players see the secret word plus a category hint.
  - The Impostor sees only the category hint, with a message such as "You do NOT know the secret
    word."
- **Clue phase:** every player submits a **single-word clue**. The clue is held privately until
  the reveal phase.
- **Reveal:** all clues (or placeholders for late/non-submissions) are shown to everyone in a
  **randomized order**, not in join order or alphabetical order, to avoid order bias.
- **Discussion:** players cross-examine clues and debate who is bluffing.
- **Vote:** each player casts one secret vote for the player they suspect is the Impostor.
- **Results:**
  - If the Impostor is the **sole** candidate with the highest vote count, they are caught.
  - If the Impostor evades detection (majority voted wrong), the Impostor receives a point.
  - Each correct voter receives a point.
  - Scores are updated and the round ends.

### 2.4 Control rules

- The **host** controls phase advancement, game selection, and bot injection.
- **Non-host players** can only act within their phase: submit a clue, cast a vote, or skip a
  timer.
- Server-side timers drive most phases; the host can override a timer with a skip action.

## 3. Technical architecture notes for the implemented system

### 3.1 Core pattern

The engine follows a **server-authoritative, Socket.IO-based** architecture:

- Express + Socket.IO on port `3000`.
- In development, Vite middleware is mounted inside Express for instant client hot reload.
- In production, Express serves the compiled SPA from `dist/`.

### 3.2 Public / private state separation

`server/roomManager.ts` is the central state manager. It exposes:

- `getPublicRoomState()` — safe to broadcast to everyone.
- `getPlayerPrivateState(room, playerId)` — only for a single player.
- `transitionToPhase()`, `submitInput()`, `castVote()`, `startPhaseTimer()`,
  `handleDisconnect()`.

### 3.3 Round state machine

- Timer-driven auto-advance is enforced server-side.
- `next-round` returns to `reveal` with a fresh round and triggers role re-assignment.
- `activeRounds` in `server/games/impostor.ts` keeps per-room impostor round data (secret word,
  impostor player id).

### 3.4 Data and assets

- `data/wordlist.json` — 100 curated, difficulty-stratified thematic nouns.
- `src/data/impostorWords.ts` — typed word helpers.
- `src/data/games.ts` — the six available game metadata entries.
- `src/theme/tokens.ts` — player color palette, spacing, radii, typography tokens.
- `src/services/sound.ts` — Web Audio notifications and haptic feedback with a mute preference.

### 3.5 Client-side responsibilities (must stay read-only for secrets)

- Join / create / reconnect flows.
- Rendering public phase UI.
- Submitting *inputs* (clues, votes) to the server.
- Displaying public lists and public results.
- Consuming private state sent by the server (`player:private-state`).

## 4. Rules the system should harden

These are recommended rules the existing engine should implement or explicitly document as
future work:

1. **Server-side clue format validation.** The current engine relies on client-side trimming and
   length caps. The server should reject or sanitize non-single-word or prohibited clues.
2. **Accountable room lifecycle.** Rooms are in-memory and are not currently cleaned up after a
   host leaves. Stable room lifecycle, idle cleanup, and graceful shutdown are needed for a real
   hosted service.
3. **Resource and rate limits.** Player count, room lifetime, replay rate, and connection limits
   should be enforced.
4. **Persistent storage.** In-memory rooms are lost on restart. A database-backed room store is
   required for production.
5. **Auth and identity.** Session tokens should be long-lived, rotated, and scoped; plus
   reconnection and guest-identity hygiene should be formalized.
6. **Transport and resilience.** Explicit reconnect strategies, heartbeat/timeout handling, and
   socket.io adapter (for multi-process or multi-instance scaling) should be formalized.
7. **Performance.** LocalStorage sync, registration sweeps, and per-room player lists should be
   profiled for growth.
8. **Observability.** Routing, heartbeats, and critical errors should be logged and monitored.

---

## 5. Current state

- The engine is **implemented** as a single-process Node/Express + Socket.IO server with a
  React frontend.
- The core "Impostor" game is **functionally present** and aligns with the classic imposter-word
  social-deduction rules.
- **Production readiness** is not yet reached: no DB, no rate limiting, no room persistence, no
  persistence of rooms on restart, and no formal hardening pass.
